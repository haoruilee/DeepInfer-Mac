\section{Design}
\label{sec:design}
Figure~\ref{fig:overview} gives the overall design, and Table~\ref{tab:mapping} lists how each part of expert parallelism carries over. This section first describes how an expert travels from the SSD to the GPU. It then follows one decoding token through a layer to find where time is lost, and ends with the two mechanisms that win it back: idle-window speculation, which is new, and an expert cache that takes the place of expert replication.

\subsection{Reading experts instead of sending tokens}
\label{sec:fetch}
In a cluster, tokens travel to the experts. On a laptop the token already sits next to the only GPU, so the expert has to travel instead, and every copy along the way costs memory that the cache could use.

\paragraph{Records and slabs.} Each expert is stored on the SSD as one page-aligned record that holds the packed weights, scales and biases of its three projections, laid out exactly as MLX \citep{mlx} lays out quantized tensors in memory. At start-up the engine allocates a \emph{slab} for each precision layout: three GPU arrays whose leading dimension indexes slots, one expert per slot. On a cache miss the engine claims a free slot and issues a single \texttt{preadv} call whose buffers point into the three arrays at that slot. Because CPU and GPU share memory, the GPU later reads the bytes exactly where the SSD put them. The files are opened with \texttt{F\_NOCACHE}, so macOS does not keep a second copy in its page cache.

\paragraph{One matmul per projection.} When the router of a layer has finished, the host reads the chosen expert ids. This is the only point in a layer where the CPU waits for the GPU. The engine maps each expert to its slot and pins the slot until the layer is done. All token-expert pairs of the layer then go through one \texttt{gather\_qmm} call per projection, with the activation function and the routing weights fused into the same compiled function. This step plays the part of the combine step in a cluster, without any communication.

\subsection{The critical path of one token}
\label{sec:chain}
Figure~\ref{fig:timeline}a shows four consecutive layers of a real decoding step. The GPU first runs attention and the router. Only then does the host know which experts the token needs, so only then can the missing ones be requested from the SSD. The GPU computes the experts once they have arrived, and the next layer cannot begin before that. The GPU and the SSD therefore take turns, and each spends much of the step waiting for the other.

This chain suggests a simple cost model. Let $a$ be the time a layer spends on attention and routing, $c$ the time spent computing experts, $m_\ell$ the number of experts missing in layer $\ell$, $b$ the size of one expert and $B$ the bandwidth of the SSD. A decoding step then takes about
\begin{equation}
t_{\text{token}} \;\approx\; \sum_{\ell=1}^{40}\Big(a + c + \frac{m_\ell\, b}{B}\Big).
\label{eq:chain}
\end{equation}
On our machine the reading term is about two thirds of a step, so the model points to three ways of making a step shorter. The first is to have fewer misses, which needs a larger cache. The second is to overlap reads with computation that does not depend on them, but inside a layer that is only the computation of already cached experts, which is short. The third is to read experts before the router asks for them, so that the SSD also works while the GPU computes. Section~\ref{sec:parallel-eval} measures each of these options against the others.

\subsection{Idle-window speculation}
\label{sec:spec}
Equation~\eqref{eq:chain} also shows when the SSD is idle: whenever the GPU runs attention or computes experts. Over a full step this idle time would be enough to read dozens of experts. Prefetching experts is a well-known idea \citep{moeoffload,pregated,moeinfinity,promoe,adapmoe}, and \citet{moeoffload} already guess the next layer's experts by applying that layer's gate to the current hidden state. We used the same predictor, yet our first prefetcher made decode slower. The traces suggested two causes, and our ablation later separated them.

The first cause is ordering. The guesses for the next layer were issued together with the current layer's misses and shared the same I/O queue, so a wrong guess could hold up a read that the token was waiting for. The second possible cause is cache pollution. A guessed expert entered the cache as if it had just been used, so a wrong guess could push out an expert that the model needed again soon.

Idle-window speculation addresses both, and it needs no training and no change to the model. When the router of a layer has finished, the engine also applies the next layer's router, with its exact scoring, to the current hidden state and keeps the top three experts as guesses. A separate thread holds these guesses back until every miss of the current layer has arrived, and only then issues their reads. The guesses therefore travel while the GPU computes, in the window where the SSD would otherwise be idle, and they never stand in front of a needed read. In addition, a guessed expert enters the cache at the end that is evicted first, similar to low-priority insertion in processor caches \citep{qureshi2007}. If the next layer uses it, it moves to the other end like any hit; if not, it is the first entry to go. A guess can never evict an expert that the current layer is using. The whole change is about forty lines in the expert store and the mixture-of-experts block. The ablation in Section~\ref{sec:parallel-eval} shows that waiting for the demand reads provides almost all of the gain, while cold insertion adds only a little. Figure~\ref{fig:timeline}b shows the effect on the same four layers: the guesses arrive while the GPU works, and the demand reads that remain are fewer and shorter.

\subsection{Replication: spending memory on the cache}
\label{sec:replication}
Copying popular experts is the part of expert parallelism that carries over most directly. A cluster replicates experts so that no GPU becomes a bottleneck; we keep recently used experts in memory so that no read is needed at all. Each hit removes one read from the chain in Equation~\eqref{eq:chain}. We use least-recently-used replacement, which beat a frequency-based policy when we replayed routing traces from the real model. The replays also showed that the size of the cache matters much more than the replacement policy.

Because the size of the cache governs decode speed, the rest of the design saves memory wherever it can. Dense FP8 weights convert to MLX's MXFP8 format without loss, so no higher-precision copy is kept. Expert reads bypass the page cache, so no expert is stored twice. Speculative reads enter the cache cold, and speculative decoding is off by default, so neither pushes useful experts out. At start-up the cache takes the memory that is free at that moment, minus a safety margin, and it always leaves at least 9\,GB to macOS. Below that, the system starts to swap and every gain is lost.

The same reasoning motivates an optional approximation. When a missing expert carries only a small share of a token's routing weight, the engine can skip it and save the read. This costs some agreement with the API on open-ended text, so it is off by default, and we did not include it in the speed measurements.
