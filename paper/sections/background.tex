\section{Background and motivation}
\label{sec:background}
\subsection{DeepSeek-V4.1-Flash}
Table~\ref{tab:model} summarizes the model. Every layer contains a mixture-of-experts block in which a router picks a few routed experts for each token, next to one shared expert. Attention combines a short sliding window with \emph{compressed sparse attention}. Keys are compressed along the sequence, and a small multi-head indexer \citep{deepseek32} chooses which compressed positions each query attends to. The selection works on two levels: one layer picks candidate blocks of positions, and the indexers of later layers only score keys inside those blocks. A few layers own the compressed caches and the others reuse them. Two layers add an \emph{Engram} module that looks up embeddings of hashed $n$-grams in very large tables, and the residual stream is mixed by Hyper-Connections with Sinkhorn-normalized matrices \citep{hyperconnections}. The release also includes draft layers for speculative decoding, called DSpark, and a vision encoder.

The released weights are stored in FP8 for the dense layers and FP4 for the experts. The reference code also rounds activations to FP8, FP4 or BF16 at fixed points during inference. These roundings matter most where the model makes discrete choices, because a score that rounds differently can change which keys the indexer keeps or which experts the router picks.

\subsection{Expert parallelism in the data center}
DeepInfer \citep{deepinfer}, DeepSeek's inference engine, serves this model on a GPU cluster with expert parallelism. Each GPU stores a subset of the experts. After routing, an all-to-all \emph{dispatch} sends every token's hidden state to the GPUs that hold its experts, and a \emph{combine} step returns the weighted results. DeepSeek uses two further techniques to keep the GPUs busy \citep{deepseekv3}. The computation of one micro-batch overlaps with the communication of another, which hides the all-to-all, and frequently used experts are copied to several GPUs, which spreads the load. Both techniques rely on having many tokens in flight at once.

\subsection{Why a laptop might be enough}
The converted model is more than ten times larger than the laptop's memory, but one decoding step touches far less. The dense part of the model fits in about a third of the memory. The experts that a single token needs add up to a few gigabytes, and if half of them are already cached, the SSD has to deliver less than two gigabytes per token. At the drive's speed, that is well under a second. A token per second therefore looks reachable, provided that the dense weights stay resident, reads go straight into GPU memory, and the cache gets every byte that is left.

Seen this way, the SSD takes the place that other GPUs hold under expert parallelism. This raises the question we study in the rest of the paper: \emph{which parts of expert parallelism still help when there is one GPU, one SSD and one sequence?}
