\section{Introduction}
Mixture-of-experts models activate only a small part of their parameters for each token \citep{switch,deepseekv3}. DeepSeek-V4.1-Flash takes this far: it has 754B parameters, but every token uses only six of the 384 experts in each layer \citep{deepseek41flash}. In the data center, DeepSeek serves the model with expert parallelism \citep{deepinfer}. The experts are spread over many GPUs, each token travels to the GPUs that hold its experts, and two techniques keep the hardware busy. One overlaps the communication of a micro-batch with the computation of another, and the other replicates experts that many tokens use.

We wanted to know whether the same model can run on a MacBook Air with 24\,GB of memory, and which of these techniques still help there. The converted model is far larger than the memory, but a single token touches only a small part of it. The attention layers, routers and other dense parts fit in a third of the memory, and the experts that one token needs are only a few gigabytes. The laptop also has a device that can hold the rest: its internal SSD. We therefore treat the SSD as the place where experts live, the role that other GPUs play in a cluster.

\method{} is built around this idea, as Figure~\ref{fig:overview} shows. When the router of a layer has chosen its experts, the engine reads each missing one from the SSD in a single call that writes directly into a slot of a GPU buffer, with no copy and no detour through the operating system's page cache. All experts of the layer then run in one gathered matrix multiplication, and recently used experts stay in memory as a cache, much as a cluster keeps copies of popular experts.

Measuring this system changed how we thought about it. A cluster has many tokens in flight, so some device always has work. A laptop decodes one token at a time, and every layer forms a strict chain: attention must finish before the router knows which experts to read, and the next layer cannot start until those experts are computed. The GPU and the SSD end up taking turns. Computing the cached experts while the missing ones load, the closest analogue of micro-batch overlap, hides only a few milliseconds per layer. Prefetching the next layer's experts should use the idle SSD, as earlier work on expert offloading suggests \citep{moeoffload}, yet in our measurements it made decode slower. An ablation shows the reason. The guesses enter the same queue as the reads the token is waiting for, and every wrong guess delays one of them.

The fix is to wait. Idle-window speculation issues the guesses only after the current layer's reads have arrived, so they run while the GPU computes and never stand in front of a needed read. It also places guessed experts where the cache evicts first. This change, about forty lines of code, turns a slowdown into an 11--27\% speed-up across every cache size we measured, and traces confirm that the SSD now works during time it used to spend idle.

The engine follows the official reference implementation operation by operation, including the model's compressed sparse attention, its Engram memory, Hyper-Connections \citep{hyperconnections}, the vision encoder and the rounding steps used in training. A test suite runs DeepSeek's PyTorch code as an oracle, so that no speed-up can silently change the model.

In summary, we make the following contributions:
\begin{itemize}
  \item We map expert parallelism to a laptop with one GPU and one SSD, and build an engine that runs every component of DeepSeek-V4.1-Flash within 24\,GB with parity tests against the reference.
  \item We describe the critical path of a decoding token, fit a simple cost model to it, and measure parallelism at six levels of the system. Only work that fills the SSD's idle time without delaying needed reads pays off.
  \item We show why next-layer expert prefetching loses on a memory-bound laptop and how idle-window speculation, an application of a known prefetch-control idea, turns it into a gain.
  \item We prove that the model's sparse-attention indexer can run on BF16 matrix units with unchanged scores under a mild condition on its scales, and we measure exact Top-$K$ screening in the style of DoSA \citep{dosa} on this model, where it saves little.
\end{itemize}
On a MacBook Air with an M4 chip, \method{} decodes 1.23 tokens per second while leaving 9\,GB of memory to macOS, agrees with DeepSeek's API on 86\% of open-ended continuation tokens, and answers a long-context retrieval question correctly at every tested length. The code, converter, tests and measurement logs are open source.
